最初に小さな機能を追加しました。しかし、より大規模な変更には、さらに堅牢なプロセスが必要です。GitHub Copilot app は組織の既存のフローに沿って作業できるように設計されており、適切なものを適切な方法で構築できます。このレッスンから数回にわたり、一般的なエージェント主導の開発プロセスを実践します。Issue を使って新機能を生成するところから始め、コードが有効で機能が期待どおりに動作することを確認し、最終的にプロジェクトへのマージを成功させます。

> [!NOTE]
> 機能のワークフローを進める間は、同じセッションを使用します。通常は作業するファイルの種類ごとに異なるセッションや PR を使用しますが、ここでは中心となる概念に集中できるように手順を短縮します。

このレッスンでは、次のことを行います。

- GitHub Issue から新しいエージェントセッションを開始します。
- **Plan** モードで要件を定義します。
- **Autopilot** モードを使用して新機能を実装します。
- コードをレビューします。
- ブラウザーキャンバスで機能を手動で検証します。

この機能の作業を続けながら、リポジトリの指示を更新し、既存の quality-checks スキルをカスタマイズして、MCP による検証を追加し、QA エージェントを作成して、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが増え、訪問者はカテゴリと出版社でゲームを絞り込む必要があります。バックログの Issue には機能の概要がありますが、カテゴリを組み合わせる方法など、コーディングの前に合意が必要な詳細があります。Plan モードで方針を決め、その後、範囲を限定した実装を Autopilot に許可します。

## 背景

AI コーディングエージェントを開発フローに導入しても、基本は変わりません。むしろ、より重要になります。多くの開発者は、次のような手順で作業します。

1. 実装する内容の詳細が記載された Issue を開きます。
2. 構築する機能の計画を立てます。
3. コードを作成してレビューします。
4. テストを実行してコードを検証します。
5. 新機能を手動で検証します。
6. pull request (PR) を作成します。
7. コードレビューと継続的インテグレーションが成功したら、コードをマージします。

> [!NOTE]
> 正確な手順はチームや組織によって異なりますが、多くの場合は上記の流れに沿っています。

この標準的な方法を守ることで、AI が生成したコードが要件を満たし、手作業で作成したコードと同じレビュー手順を経るようにします。

## セッションモード

**セッションモード**は、エージェントがどれだけ自律的に作業するかを制御します。プロンプトフィールドの下にあるドロップダウンから設定し、いつでも変更できます。

- **Interactive**: ユーザーとエージェントが共同で作業します。エージェントは変更を提案し、次に進む前にユーザーの入力を待ちます。
- **Plan**: エージェントが最初に計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントが完全に自律して作業し、入力を待たずにコードを書き、テストを実行し、反復します。

まず Plan モードで開始して計画をレビューし、その後 Autopilot で実装します。

## Issue からセッションを開始する

開始前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys のリポジトリフォルダーを選択し、リポジトリの上部ナビゲーションで **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。これはテンプレートに含まれる既存の Issue なので、新たに作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選択します。

    ![GitHub Copilot app の Issue ビューで、New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに添付されていることを確認し、モードセレクターで **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` の実行を依頼します。ターミナルでは動作するのにセッションで動作しない場合は、アプリの PATH またはバージョンマネージャーの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで npm を再インストールしないでください。

## フィルター機能を計画する

計画を立てることで、Copilot がコードを書く前にアプローチをレビューできます。Issue から開始したため、Copilot は機能のリクエストをすでにコンテキストとして持っています。次を送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、Issue の受け入れ条件と計画を照らし合わせます。カテゴリと出版社による絞り込み、アクセシブルなコントロール、データアクセスの変更、テストが含まれていることを確認してください。複数のカテゴリをどのように組み合わせるか、一致するゲームがない場合にどうなるかなど、不明確な動作について話し合います。

計画には、プロジェクトの既存ツールを使った lint、ユニットテスト、E2E テスト、型チェックを含めます。フィルター機能の実装とテストに範囲を絞ってください。PR は品質ワークフローの完了後に作成します。計画の修正は承認前に依頼し、後の検証に使えるよう Issue の URL と合意した明確化事項を控えておきます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan**、または使用中のバージョンで表示される同等のオプションを選択します。承認するとモードも切り替わると思い込まず、現在のモードを確認してください。モード表示が **Autopilot** になっていることを確認します。

Copilot が実装を開始します。作成した計画に沿って作業し、コードを生成してテストも実行しながら、プロセスを反復して進めます。

> [!NOTE]
> 承認するとすぐに実装が始まる場合があるため、先に計画をレビューしてください。依存関係の不足やポート競合が報告された場合は、チェックを完了と判断する前にセットアップの問題を解決します。停止してよいのは、自分で起動したサーバーだけです。

## 実装をレビューして検証する

生成されたコードも、ほかのコードと同じようにマージ前にレビューします。コードをレビューし、サイトを実行して問題がないことを確認しましょう。

1. **Changes** を開き、フィルター機能の実装とテストを確認します。
2. 複数カテゴリと出版社の組み合わせも含め、結果を Issue と承認した明確化事項に照らし合わせます。変更が既存のリポジトリの指示に従っていることを確認します。
3. lint、ユニットテスト、E2E テスト、型チェックの出力を確認します。スキップされたチェックは成功ではありません。
4. 実装を承認する前に失敗を解消し、該当するチェックを再実行します。Playwright の E2E 設定はビルドしてプレビューを配信し、ローカルサーバーを再利用できるため、テスト対象が以前のレッスンではなく、この worktree のサーバーであることを確認します。

## 新機能を確認する

コードに問題がないように見えても、実際に動くか確認しましょう。前と同じようにアプリを起動し、ブラウザーキャンバスでサイトを開きます。

1. 次のプロンプトを使い、アプリを起動してブラウザーキャンバスでページを開くよう Copilot に依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザーウィンドウが開きます。
3. カテゴリを選択し、結果が一致することを確認します。フィルターを解除してから出版社を選択し、結果がその出版社に一致することを確認します。
4. カテゴリと出版社のフィルターを組み合わせ、Issue と承認済みの計画に照らし合わせます。複数のカテゴリを指定できる場合は、合意した組み合わせの動作を確認します。
5. ゲームが一致しない組み合わせを試し、空の状態を確認します。フィルターを解除またはリセットし、一覧全体が戻ることを確認します。
6. 確認が終わったら、次のプロンプトを使い、このセッションで起動した開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンに向けてセッションを保持する

フィルター機能の PR は、まだ作成またはマージしないでください。レッスン 4 から 8 まで、同じセッション、worktree、ブランチを使用します。次はカスタム指示をフィルター機能のコードに適用し、スキルと QA の改善を追加してから、レッスン 8 でそれらをまとめた PR を作成してマージします。開発サーバーを停止した後、セッションはそのままにしておきます。次のレッスンで同じセッションに戻ります。

## まとめと次のステップ

さまざまなエージェントモードを使って機能を構築し、レビューしました。このレッスンでは、次のことを行いました。

- GitHub Issue から新しいエージェントセッションを開始しました。
- **Plan** モードで要件を定義しました。
- **Autopilot** モードで新機能を実装しました。
- コードをレビューしました。
- ブラウザーキャンバスで機能を手動で検証しました。
